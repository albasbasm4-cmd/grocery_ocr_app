# وثيقة القرارات المعمارية (Architecture Decisions)
## نظام إدارة مخزون ونقاط بيع البقالة للهواتف (Grocery POS & Inventory Mobile App)

تحدد هذه الوثيقة المبادئ المعمارية الصارمة والقرارات الهندسية المعتمدة لتطوير التطبيق. هذه القرارات ملزمة في جميع مراحل المشروع ولا يجوز تجاوزها.

---

### 1. المتجر هو وحدة العزل الرئيسية (Multi-Tenancy & Store Isolation)
- **كل الجداول مرتبطة بالمتجر**: تحتوي جميع جداول المعاملات والبيانات على حقل `store_id` (وليس `user_id` فقط).
- **إدارة الأعضاء والصلاحيات**: يوجد جدول وسيط:
  ```sql
  store_members (
    id uuid primary key,
    store_id uuid references stores(id),
    user_id uuid references auth.users(id),
    role text check (role in ('owner', 'staff')),
    created_at timestamptz default now()
  )
  ```
- **حسابات فردية**: كل موظف يمتلك حساب دخول خاص به ولا يُشارك حساب المالك مع العاملين.

---

### 2. الصلاحيات تُفرض في قاعدة البيانات (RLS Enforcement)
- **الأمان أولاً**: تُفرض الصلاحيات عبر سياسات أمان مستوى الصفوف (Row Level Security - RLS) في PostgreSQL.
- **دور الواجهة**: إخفاء الأزرار والعناصر في الواجهة هو لتحسين تجربة المستخدم فقط (UX)، بينما الحماية وحظر العمليات غير المصرح بها يقعان حصراً على عاتق RLS ودوال RPC.

---

### 3. العمليات الحساسة عبر دوال PostgreSQL الذرية (Atomic RPC Transactions)
- **لا تعديلات متفرقة من العميل**: كافة عمليات:
  - إنشاء حركات البيع (Checkout / Sales)
  - المرتجعات (Returns)
  - تسوية وجرد المخزون (Stock adjustments)
  تتم حصراً عبر دوال PostgreSQL (Stored Procedures / RPC) تُنفذ داخل Transaction ذرية واحدة (`BEGIN ... COMMIT`).
- في حال فشل أي شرط (مثل عدم توفر المخزون الكافي)، يتم عمل Rollback كامل دون ترك بيانات غير متسقة.

---

### 4. التعامل المالي الدقيق (Financial Integrity)
- **منع الأخطاء الحسابية العائمة**:
  - يمنع منعاً باتاً استخدام `float` أو `number` العادي في JavaScript للقيم المالية.
  - تستخدم مكتبة `decimal.js` في الواجهة لجميع العمليات الحسابية (الجمع، الضرب، الضرائب، الخصم).
  - يُستخدم نوع `numeric` / `decimal` بدقة كافية في قاعدة البيانات (مثل `numeric(12, 2)`).
- **العملة قابلة للضبط**: العملة تُحدد من إعدادات المتجر عبر حقلي `currency_code` و `currency_symbol`.

---

### 5. الحذف المنطقي للمنتجات (Soft Delete)
- **عدم الحذف الفعلي**: لا تُحذف المنتجات من قاعدة البيانات (`DELETE`).
- **التعطيل**: يتم تعطيل المنتجات عبر حقل `is_active = false`، وذلك لضمان بقاء الفواتير والتقارير وحركات المخزون التاريخية سليمة وقابلة للتدقيق.

---

### 6. واجهة مستخدم مخصصة للهواتف واستخدام اليد الواحدة (Mobile-First RTL UX)
- **عربية بالكامل (RTL)**: اتجاه الواجهة عربي من اليمين إلى اليسار (`dir="rtl"`) مع خط عربي واضح وعالي الدقة (Cairo).
- **استخدام بيد واحدة (Thumb-Zone Design)**: الأزرار الحيوية وسلة البيع موضوعة في متناول إبهام اليد الواحدة.
- **أزرار لمس كبيرة**: مساحات لمس مريحة (Touch targets لا تقل عن 48px) تمنع الضغط الخاطئ أثناء البيع السريع.

---

### 7. المركزية في الترجمة والنصوص (i18n Centralization)
- كل نص يظهر في واجهة المستخدم يمر عبر قاموس ترجمة مركزي (`src/i18n/`).
- لا تُكتب أي نصوص ثابتة (Hardcoded strings) داخل المكونات البرمجية.

---

### 8. سرية المفاتيح وعدم كشفها (Zero-Secrets Leakage)
- لا يُسمح بتضمين أي مفتاح سري (مثل مفاتيح Groq، Gemini، أو `SUPABASE_SERVICE_ROLE_KEY`) داخل كود الواجهة أو في مستودع GitHub.
- المفاتيح تُخزن حصراً في:
  - Supabase Project Secrets (لاستخدامها داخل Edge Functions).
  - GitHub Actions Secrets (لعمليات البناء والنشر المؤتمتة).
- الواجهة تستدعي الـ AI عن طريق Supabase Edge Function فقط، ولا تتصل بأي مزود ذكاء اصطناعي بشكل مباشر.

---

### 9. جودة الكود وبنية المجلدات و TypeScript الصارم
- **تقسيم معياري**:
  - `src/components`: المكونات القابلة لإعادة الاستخدام.
  - `src/pages`: صفحات وشاشات التطبيق.
  - `src/hooks`: خطافات مخصصة (Custom Hooks).
  - `src/lib`: المساعدات والتهيئة للمكتبات الخارجية.
  - `src/services`: الاتصال بقاعدة البيانات ودوال RPC.
  - `src/types`: تعريفات الأنواع (TypeScript Interfaces & Types).
  - `src/i18n`: قواميس النصوص المركزية.
- **TypeScript Strict**: منع استخدام نوع `any` بشكل تام، والاعتماد على الفحص الصارم للأنواع (Strict Mode).

---

### 10. نموذج الصلاحيات المحدث والانضمام للمتاجر وحماية PIN (المرحلة 13)
- **رمز PIN يخص المتجر**: رمز PIN يُنشأ للمتجر مرة واحدة عند تأسيسه بواسطة المالك، ولا يمتلك الموظفون أي PIN.
- **إلغاء قيود PIN عن العمليات التشغيلية للمالك**:
  - إضافة وتعديل وتفعيل وتعطيل وحذف المنتجات والتصنيفات.
  - تسوية وجرد المخزون.
  - إلغاء الفواتير وإرجاع المبيعات.
  - استيراد وتصدير البيانات والنسخ الاحتياطي.
  كافة هذه العمليات ينفذها المالك مباشرة دون طلب رمز PIN.
- **حصر اشتراط PIN في 5 إجراءات إدارية فقط**:
  1. إضافة موظف (سواء بإنشاء حساب أو قبول طلب انضمام).
  2. تعديل صلاحيات موظف (`permission` أو `can_sell`).
  3. تعطيل موظف أو حذفه من المتجر.
  4. تغيير رمز PIN الإداري.
  5. إعادة توليد رمز الانضمام للمتجر.
- **مصفوفة صلاحيات الموظفين**:
  - `owner`: صلاحيات كاملة ورؤية سعر التكلفة والإشراف الإداري. متجر واحد يمتلك مالكاً واحداً فقط لا يمكن حذفه أو تعطيله.
  - `staff` مع صلاحية `write`: يستطيع إضافة وتعديل المنتجات والتصنيفات وتسوية المخزون، ولا يرى سعر التكلفة ولا يعطل المنتجات ولا يحذفها ولا يدير الموظفين.
  - `staff` مع صلاحية `read`: عرض المنتجات والمخزون دون تعديل.
  - `can_sell`: مفتاح منطقي مستقل يحدد إمكانية إتمام الفواتير عبر نقطة البيع (POS).
- **نظام الانضمام عبر الرموز (Join Codes)**:
  - رمز فريد من 6-8 أحرف لكل متجر.
  - رسائل أخطاء موحدة (`رمز المتجر غير صحيح أو غير متطابق.`) لمنع استكشاف المتاجر وتخمين الرموز.
  - انتهاء صلاحية الطلبات تلقائياً بعد 7 أيام.
  - حد أقصى 5 طلبات انضمام يومياً لكل مستخدم.
  - إمكانية حظر المتقدم المزعج من قبل المالك.
- **استعادة PIN عبر البريد الإلكتروني**:
  - رمز تحقق آمن مكون من 6 أرقام عشوائية.
  - يُخزن كـ SHA-256 hash فقط دون حفظ الرمز الأصلي.
  - صلاحية 10 دقائق، حد أقصى 5 محاولات فاشلة قبل الإبطال.
  - فاصل زمني 60 ثانية وحد أقصى 3 رموز بالساعة.
  - إبطال كافة الجلسات النشطة فور إعادة التعيين مع إشعار أمني لبريد المالك.
- **سجل التدقيق الأمني (Store Audit Log)**:
  - توثيق ذري لكافة العمليات الحساسة مع معرّف الفاعل والمستهدف والبيانات التفصيلية.
