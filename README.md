# تطبيق إدارة مخزون ونقاط بيع البقالة (Grocery POS & Inventory Mobile App)

تطبيق ويب مخصص للهواتف المحمولة يُحزَّم كتطبيق Android (APK) عبر Capacitor، بواجهة عربية بالكامل (RTL). صُمم خصيصاً لأصحاب وموظفي محلات البقالة والمتاجر لتسريع عمليات البيع، وإدارة المخزون بدقة، ومسح الباركود بالكاميرا أو إدخال الرمز يدوياً.

---

## 📱 مميزات التطبيق الأساسية (خارطة الطريق)
- **قراءة الباركود السريعة**: عبر الكاميرا باستخدام Capacitor ML Kit Barcode Scanning على أجهزة أندرويد، ومكتبة ZXing كحل احتياطي لبيئة الويب.
- **إدخال SKU يدوي**: شاشة سريعة للإدخال اليدوي للأرقام الصغيرة تحت الباركود.
- **إدارة التصنيفات والمنتجات**: بحث حي وترتيب أبجدي عربي، تطبيع عربي ذكي (`normalize_arabic`)، وتعطيل المنتجات دون حذفها للحفاظ على سجل الفواتير.
- **سلة بيع آمنة (POS)**: عمليات بيع فورية تخصم من المخزون بأمان عبر معاملات ذرية (Database RPC Transactions) تدعم خاصية منع التكرار (Idempotency).
- **أمان وصلاحيات متعددة المتاجر**: عزل تام بين المتاجر عبر `store_id` وسياسات Row Level Security (RLS)، مع نظام أدوار (مالك / موظف) وحماية بالـ Admin PIN.
- **مساعد ذكاء اصطناعي (AI Assistant)**: للإجابة عن أسئلة المخزون والمبيعات عبر Supabase Edge Functions.
- **تصدير كود Java**: تصدير بيانات المنتجات إلى كود Java لدمجها مع الأنظمة الأخرى.

## 🛠️ المكدس التقني (Tech Stack)
- **الواجهة الأمامية**: React 18 + Vite + TypeScript + Tailwind CSS
- **إدارة الحسابات والبيانات**: Supabase (PostgreSQL + RLS + RPC + Auth)
- **المنطق الخلفي**: Supabase Edge Functions (Deno / TypeScript)
- **الحسابات المالية**: `decimal.js` (تجنب أخطاء float في JavaScript)
- **مسح الباركود**: Capacitor ML Kit Barcode Scanning + ZXing Fallback
- **التحزيم المحمول**: Capacitor + GitHub Actions CI/CD لبناء حزم APK

## 🗄️ تفاصيل قاعدة البيانات (المرحلة 1)

### 1. الجداول الأساسية
1. **`stores`**: معرّف المتجر، الاسم، رمز العملة واسمها.
2. **`store_members`**: العزل والأدوار (`owner` و `staff`) مع مفتاح مركب `(store_id, user_id)`.
3. **`admin_pins`**: تجزئة رمز PIN للمدير بـ bcrypt ومتابعة المحاولات الخاطئة والقفل المؤقت (15 دقيقة).
4. **`admin_sessions`**: جلسات التحقق من الـ PIN بصلاحية 10 دقائق لتنفيذ العمليات الإدارية الحساسة.
5. **`categories`**: التصنيفات مع قيد فريد على `(store_id, name_normalized)`.
6. **`products`**: المنتجات مع أسعار `numeric(14,2)` وكمية مخزون `numeric(14,3)`، وقيد فريد للباركود لكل متجر، مع الحذف المنطقي (`is_active = false`).
7. **`customers`**: سجل العملاء ورصيد الديون المستحقة (`balance`).
8. **`sales`**: الفواتير، طرق الدفع (`cash` أو `credit`)، ومعرّف العميل، وحقل `client_uuid` لمنع التكرار (Idempotency).
9. **`sale_items`**: عناصر الفاتورة مع لقطات تاريخية للأسعار والتكلفة (`product_name_snapshot`, `unit_price_snapshot`, `cost_price_snapshot`).
10. **`stock_movements`**: سجل حركات المخزون للتدقيق لجميع الحالات (`sale`, `return`, `purchase`, `adjustment`, `damage`, `void`).
11. **`customer_payments`**: تسديدات ديون العملاء وخصمها من الرصيد.

### 2. التطبيع العربي والبحث السريع
- **`normalize_arabic(text)`**: دالة مدمجة تزيل التشكيل، التطويل، وتوحد الألف والتاء المربوطة والألف المقصورة، وتحول الأرقام الهندية للاتينية، مع اختزال المسافات.
- تريجرات تلقائية عند الإضافة أو التعديل لملء `name_normalized`.
- فهارس ثلاثية الأحرف **`pg_trgm`** (GIN) للبحث الحي الفوري.

### 3. سياسات الأمان (Row Level Security - RLS)
- RLS مفعل على كل الجداول.
- القراءة محصورة في أعضاء المتجر الحالي فقط (`is_store_member`).
- التعديل الإداري للمالك فقط، ويشترط جلسة PIN فعالة (`has_active_admin_session`) لتعديل الأسعار والتعطيل وتعديل المخزون.
- المبيعات وحركات المخزون محظورة من أي إدراج أو تعديل مباشر من العميل وتتم حصراً عبر دوال الـ RPC.

### 4. دوال RPC الذرية (Atomic Database Transactions)
- `create_store(name, currency_code, currency_symbol)`: إنشاء متجر وتعيين المنشئ كمالك.
- `set_admin_pin(store_id, new_pin, old_pin)`: تعيين أو تحديث الـ PIN للمالك.
- `verify_admin_pin(store_id, pin)`: التحقق بـ bcrypt، وقفل 15 دقيقة بعد 5 أخطاء، وإصدار جلسة صالحة لـ 10 دقائق.
- `process_sale(...)`: قفل الصفوف (`FOR UPDATE`)، التحقق من المخزون، خصمه، إنشاء الفاتورة وعناصرها، وحركات المخزون، وتحديث رصيد العميل الآجل، ودعم الـ Idempotency.
- `void_sale(sale_id, reason)`: إلغاء الفاتورة بالكامل وإعادة المخزون ورصيد العميل.
- `return_items(sale_id, items, reason)`: إرجاع جزئي/كلي مع التحقق من عدم تجاوز الكمية المباعة.
- `adjust_stock(product_id, new_quantity, reason)`: تسوية يدوية مع تسجيل الحركة.
- `record_customer_payment(customer_id, amount)`: تسجيل سداد وتخفيض الدين.
- `bulk_upsert_products(store_id, rows, mode)`: استيراد وتحديث جماعي مع تقرير بالصفوف المقبولة والمرفوضة وسبب كل رفض.

### 5. التقارير الإحصائية (Views & Analytics)
- `view_low_stock`: المنتجات التي وصلت للحد الأدنى أو أقل.
- `view_expiring_soon`: المنتجات التي تنتهي صلاحيتها خلال 30 يوماً.
- `get_daily_sales(store_id, days)`: إجمالي المبيعات اليومية ونسب الكاش والآجل.
- `get_top_products(store_id, limit)`: أكثر المنتجات مبيعاً من حيث الكمية والإيراد.
- `get_profit_summary(store_id, from_date, to_date)`: ملخص الأرباح وهوامش الربح استناداً إلى لقطات التكلفة التاريخية.

### 6. تشغيل الاختبارات البرمجية لقاعدة البيانات
يمكنك تشغيل ملف الاختبارات داخل محرّر SQL في لوحة تحكم Supabase أو عبر Supabase CLI:
```bash
supabase db test
# أو تنفيذ الملف المباشر:
# supabase/tests/database_test.sql
```

## 🚀 تشغيل المشروع محلياً

1. استنسخ المستودع:
   ```bash
   git clone https://github.com/albasbasm4-cmd/grocery_ocr_app.git
   cd grocery_ocr_app
   ```
2. ثبّت الحزم:
   ```bash
   npm install
   ```
3. أنشئ ملف البيئة:
   ```bash
   cp .env.example .env.local
   ```

6. شغّل خادم التطوير:
   ```bash
   npm run dev
   ```

## المرحلة الرابعة: إدارة المنتجات والتصنيفات

- أضيفت شاشة المنتجات ببحث حي عربي بعد التطبيع، وفلاتر التصنيف والمخزون المنخفض وقرب الصلاحية والمنتجات المعطلة.
- تحميل المنتجات تدريجي على دفعات من خلال RPC آمن في قاعدة البيانات لتقليل حمل الهاتف، مع ترتيب أقسام المنتجات أبجدياً بـ `Intl.Collator('ar')` في الواجهة.
- أضيفت شاشة إدارة التصنيفات، وتُزرع التصنيفات المقترحة تلقائياً عند إنشاء متجر جديد. يتطلب إنشاء/تعديل/حذف التصنيف جلسة PIN للمالك، ويمنع قيد قاعدة البيانات حذف تصنيف مرتبط بمنتجات.
- نماذج المنتجات تتحقق من الأسعار والكميات العشرية، وتتحقق من تكرار الباركود برسالة توضح اسم المنتج المتعارض. لا يُعدّل رصيد المخزون مباشرة؛ الرصيد الافتتاحي والتسويات تستخدم RPC `adjust_stock` مع سبب مسجل.
- الموظف يقرأ المنتجات والتصنيفات وحركة المخزون فقط، ولا يظهر له سعر التكلفة. قراءات تكلفة المنتجات محمية عبر RPC للمالك فقط.
- أضيفت تفاصيل المنتج وسجل حركات المخزون، مع إبطال TanStack Query بعد التغييرات.
- migrations للمرحلة الرابعة: `20261107000009_phase4_default_categories_and_pin_rls.sql` و`20261107000010_phase4_owner_product_cost_rpc.sql`.

## المرحلة الخامسة: المسح بالكاميرا وقراءة SKU

- أضيف `BarcodeScanner` بمسح ML Kit على Android وZXing للمتصفح فقط، ويدعم EAN-13 وEAN-8 وUPC-A وUPC-E وCode 128 وQR. يتضمن إذن الكاميرا، المعاينة وخط التوجيه والفلاش، اهتزازاً وصوتاً عند القراءة، ومنع تكرار الرمز لمدة 1.5 ثانية.
- حقل إدخال يدوي دائم يبحث في الباركود والـ SKU. تُعرض قائمة اختيار عند تعدد النتائج. في المنتجات يفتح المنتج المطابق، ويُعبّأ الباركود في نموذج جديد للمالك إذا لم يوجد؛ وفي البيع يضاف المنتج إلى السلة مباشرة، ويظهر تنبيه إن لم يوجد.
- OCR للرقم الصغير معزول في `src/services/smallNumberOcr.ts`، ويُعطّل عبر `VITE_ENABLE_SMALL_SKU_OCR=false`. النتيجة تُعرض في نافذة قابلة للتعديل ولا تُحفظ إلا بعد التأكيد.

### اختبار Android على جهاز فعلي

1. ثبّت Android Studio وAndroid SDK، ووصل جهازاً مفعلاً عليه USB debugging أو استخدم جهازاً فعلياً من Android Studio.
2. نفّذ `npm ci` ثم `npm run cap:sync`، وافتح Android عبر `npm run cap:android`، ثم شغّل التطبيق على الجهاز.
3. جرّب السماح بالكاميرا، ثم امسح باركود EAN-13 أو EAN-8 أو UPC أو Code128 أو QR، وتأكد من ظهور الرمز مرة واحدة ومن الصوت والاهتزاز والفلاش.
4. ارفض إذن الكاميرا وتأكد من إرشاد المستخدم إلى إعدادات التطبيق، ثم امنح الإذن من إعدادات Android وأعد المحاولة. اختبر أيضاً إدخال الباركود والـ SKU بالأرقام العربية واللاتينية، ورمزاً غير موجود، ونتائج متعددة.
5. جرّب OCR من نموذج المنتج. عدّل النص المقروء أو أعد الالتقاط، وتأكد أن حقل SKU لا يتغير قبل الضغط على «اعتماد الرقم».

لم يُجر اختبار على جهاز فعلي ضمن هذه المرحلة؛ الخطوات أعلاه توثّق الاختبار المطلوب.


## المرحلة السادسة: شاشة البيع، السلة، الفواتير، والعملاء

- **شاشة البيع (POS) وإدارة السلة**:
  - شاشة POS متجاوبة للأجهزة المحمولة مع زر مسح باركود بارز، وبحث حي وفوري بالاسم والباركود والـ SKU.
  - سلة بيع تدعم زيادة/نقصان الكمية، الحذف، والإدخال المباشر للكميات الصحيحة والعشرية للمنتجات بالوزن (كيلو وغرام).
  - حساب المجموع الفرعي والخصومات والإجمالي لحظياً باستخدام مكتبة `decimal.js` مع تفادي حسابات float تماماً.
  - فحص مباشر للمخزون ومنع تجاوز الكمية المتاحة مع تنبيه باسم المنتج والكميات المتبقية.
  - حفظ السلة تلقائياً في `localStorage` لاستعادتها حال إغلاق التطبيق غير المقصود، مع زر لتفريغ السلة عند الحاجة.

- **الخصم والدفع**:
  - خيارات خصم مرنة: مبلغ ثابت أو نسبة مئوية (%)، مع التحقق الأمني من عدم تجاوز الخصم لإجمالي الفاتورة.
  - خيارات الدفع: نقدي أو آجل (ذمم). يتطلب البيع الآجل اختيار عميل من القائمة أو إضافة عميل جديد سريعاً (الاسم والهاتف).

- **تأكيد البيع وحفظ الفاتورة**:
  - توليد `client_uuid` فريد في الواجهة لمنع التكرار (Idempotent)، وتعطيل زر التأكيد أثناء التنفيذ لمنع النقر المزدوج.
  - استدعاء آمن لدالة `process_sale` في PostgreSQL داخل Transaction ذرية واحدة: قفل المنتجات، خصم المخزون، حفظ لقطات (snapshots) الأسماء والتكاليف، تسجيل حركات المخزون، وتحديث رصيد العميل إن كانت آجلة.
  - تفريغ السلة وعرض نافذة النجاح مع ملخص الإيصال وخيارات الطباعة والمشاركة.

- **سجل الفواتير والمبيعات**:
  - شاشة مخصصة لعرض الفواتير مصنفة حسب التاريخ (اليوم، أمس، آخر 7 أيام، هذا الشهر)، طريقة الدفع (نقدي/آجل)، والحالة (مكتملة/ملغاة).
  - نافذة تفاصيل الفاتورة تعرض لقطات البنود والأسعار. الموظف يرى الفواتير وقراءة البنود فقط؛ المالك يرى لقطة التكلفة وصافي الأرباح لكل بند عبر RPC خاص.
  - إلغاء الفاتورة بالكامل (`void_sale`) وإرجاع جزئي لبنود محددة (`return_items`) مقتصران على المالك فقط، ويشترطان إدخال سبب مكتوب واضح والتحقق من رمز PIN الإداري.

- **إدارة العملاء والديون**:
  - شاشة لحسابات العملاء تعرض إجمالي ديون المتجر المستحقة محسوبة بـ `decimal.js`.
  - قائمة العملاء مع تصفية المدينين فقط، وبحث بالاسم والهاتف، وعرض الرصيد المستحق.
  - صفحة تفاصيل العميل تعرض سجل فواتيره الآجلة وسجل دفعات السداد السابقة.
  - تسجيل دفعات سداد الديون نقدياً عبر استدعاء RPC `record_customer_payment` الذرية.
  - حماية رصيد العميل `customers.balance` في قاعدة البيانات ومنع تعديله المباشر عبر REST.

- **طباعة ومشاركة الإيصال والطابعات الحرارية**:
  - توليد إيصال PDF أنيق قياس 80 مم يدعم اللغة العربية والخطوط المحلية وتنسيق RTL.
  - مشاركة الإيصال عبر `@capacitor/share` على هواتف Android وحفظه في مجلد التخزين المؤقت عبر `@capacitor/filesystem`، مع دعم Web Share وتنزيل المتصفح.
  - خدمة طابعة حرارية تجريدية ومولد أوامر ESC/POS في `src/services/thermalPrinterService.ts` لتسهيل ربط طابعات البلوتوث وUSB مستقبلاً دون تعديل منطق التطبيق.

- **تغييرات قاعدة البيانات**:
  - ملف الهجرة `supabase/migrations/20261107000011_phase6_return_items_owner_pin.sql`:
    - قيد دور المالك والتحقق من PIN وفرض سبب مكتوب في `void_sale` و`return_items`.
    - حماية حقل `balance` بجدول `customers` من التعديل المباشر وحصره على الـ RPCs.
    - إضافة RPC `get_sale_items_cost` لاسترجاع لقطات التكلفة للمالك فقط وحجبها عن الموظف.

## المرحلة 7: الاستيراد والتصدير والنسخ الاحتياطي (Phase 7)

تم إنجاز نظام متكامل وشامل لاستيراد وتصدير المنتجات والنسخ الاحتياطي الآمن وفق متطلبات البقالة:

- **استيراد المنتجات من Excel و CSV**:
  - يدعم صيغ `.xlsx`, `.xls`, و `.csv`.
  - معالجة ترميز CSV بنظام UTF-8 وإزالة علامة ترتيب البايتات (BOM: `\uFEFF`) لضمان عدم تخرب الأحرف العربية أثناء القراءة أو الحفظ.
  - تحليل وفك ترميز الملفات الكبيرة في خيط معالجة منفصل (Web Worker: `src/workers/importParserWorker.ts`) باستخدام مكتبة SheetJS لضمان عدم تجميد الواجهة حتى 10,000 صف.

- **تحميل القالب النموذجي**:
  - زر مباشر ينزل ملف Excel قياسي يحتوي على الأعمدة المعتمدة بالترتيب:
    1. اسم المنتج (إلزامي)
    2. التصنيف
    3. الباركود
    4. الرقم الصغير (SKU)
    5. الوحدة (حبة، كيلو، غرام، كرتون، حزمة، صندوق، أخرى)
    6. سعر البيع (إلزامي)
    7. سعر الشراء (التكلفة)
    8. الكمية في المخزون
    9. الحد الأدنى للمخزون
    10. تاريخ الصلاحية (YYYY-MM-DD)
  - تضمن القالب صفاً نموذجياً معبأً ببيانات بقالة واقعية لتسهيل الإدخال.

- **معاينة وربط الأعمدة التلقائي واليدوي**:
  - عرض أول 5 صفوف في جدول معاينة فوري وسريع.
  - التعرف الذكي التلقائي على أسماء الأعمدة الشائعة باللغتين العربية والإنجليزية.
  - إمكانية التعديل اليدوي السهل لتعيين أي عمود إلى حقل النظام المقابل.

- **التحقق من البيانات وكشف التكرار والتصنيفات الجديدة**:
  - التحقق من وجود الحقول الإلزامية (الاسم وسعر البيع).
  - تحويل الأرقام الهندية والإنجليزية تلقائياً والتأكد من أنها قيم عددية غير سالبة.
  - فحص الباركودات المكررة داخل نفس ملف الاستيراد وتنبيه المستخدم بها.
  - كشف التصنيفات المذكورة في الملف وغير الموجودة مسبقاً في قاعدة بيانات المتجر، مع خيار لإنشائها تلقائياً بعد موافقة المستخدم.

- **سلوك التعامل مع تكرار الباركود في المتجر**:
  - خيار **تخطي الموجود (Skip)**: الإبقاء على بيانات المنتج الحالية في المتجر دون تعديل.
  - خيار **تحديث الموجود (Update)**: تحديث سعر البيع، سعر الشراء، كمية المخزون، والحد الأدنى للمنتج المسجل في المتجر.

- **الرفع والمعالجة على دفعات (Batch Processing)**:

- **تقرير النتائج وتنزيل المرفوضات**:
  - إحصائيات دقيقة: إجمالي الصفوف، المضاف جديداً، المحدث، المتخطى، والمرفوض.
  - تنزيل تقرير Excel مفصل للصفوف المرفوضة يوضح رقم الصف وبياناته وسبب الرفض المباشر.

- **تصدير المنتجات ومشاركتها**:
  - نافذة تصدير تتيح اختيار نطاق التصدير: لجميع المنتجات أو حسب تصنيف محدد.
  - دعم التصدير بصيغتي Excel (.xlsx) و CSV (UTF-8 مع BOM للحفاظ على الحروف العربية).
  - مشاركة الملف عبر `@capacitor/share` وحفظه في مجلد التخزين على Android أو تنزيله عبر المتصفح.

- **النسخ الاحتياطي الشامل للمتجر (Full JSON Backup)**:
  - استدعاء RPC آمن `export_full_store_backup` في PostgreSQL يخضع لحماية دور المالك وجلسة رمز PIN النشطة حصراً.
  - تصدير ملف JSON متكامل يتضمن: بيانات المتجر وإعداداته، شجرة التصنيفات والمنتجات (شاملة لقطات التكلفة وتواريخ الصلاحية)، حسابات العملاء وأرصدة الديون الحالية، الفواتير التاريخية وبنودها كاملة، وسجل حركات المخزون ودفعات سداد الديون.

## المرحلة 9: المساعد الذكي وتصدير Java

- صفحة `/ai-chat` تقدم محادثة عربية، أسئلة جاهزة، عرض حالة الكتابة ورسائل الأخطاء. ترسل الرسالة إلى Supabase Edge Function `ai-chat` فقط؛ لا يتصل المتصفح بمزود النموذج مباشرة.
- وظيفة `ai-chat` تتحقق من JWT وعضوية المتجر ودور العضو، وتطبق حد 20 طلباً في الدقيقة لكل مستخدم/متجر، وتستخدم استعلامات RPC محددة للقراءة فقط. سجل المحادثة لا يُقبل من العميل لتقليل حقن السياق. بيانات التكلفة والأرباح لا تعاد للموظف من دوال SQL.
- **أسرار الذكاء الاصطناعي:** أضف `GROQ_API_KEY` و `GEMINI_API_KEY` إلى Supabase Secrets من لوحة التحكم أو CLI الآمن. لا تضع هذه الأسرار في `.env` أو GitHub أو كود الواجهة.
- **نظام التحويل التلقائي الصامت بين النماذج (Multi-Model Silent Failover):**
  - **سلسلة نماذج Groq (المزود الأساسي للسرعة الفائقة - مهلة 10 ثوانٍ للنموذج):**
    1. `openai/gpt-oss-120b` (النموذج القيادي للذكاء والاستدلال)
    2. `openai/gpt-oss-20b` (النموذج السريع عالي الإنتاجية)
    3. `qwen/qwen3.8-27b` (النموذج التجريبي المتقدم)
    4. `qwen/qwen3.6-27b` (النموذج الاحتياطي التجريبي)
  - **سلسلة نماذج Google Gemini (المزود الاحتياطي - مهلة 15 ثانية للنموذج):**
    1. `gemini-3.8-flash` (النموذج الأكثر ذكاءً للوكلاء واستدعاء الأدوات)
    2. `gemini-3.5-flash` (النموذج المتوازن عالي الكفاءة)
    3. `gemini-3.5-flash-lite` (النموذج فائق السرعة والاقتصاد)
    4. `gemini-2.5-flash` (النموذج المستقر)
  - **آلية التحويل:** عند فشل أي نموذج بحالات 429 (نفاد الحصة)، 404 (نموذج متقاعد/غير موجود)، 401، 403، 408، أي 5xx، انقطاع اتصال، انتهاء المهلة، أو 400 يحتوي على `tool_use_failed`؛ ينتقل الطلب فوراً وفي نفس الجلسة إلى النموذج التالي.
  - **الحدود والأمان:** حد أقصى 6 محاولات فعلية للطلب الواحد، ومهلة كلية نحو 45 ثانية. التحويل مدمج داخل حلقة الأدوات (Tool Calling) بحيث يكمل النموذج التالي من نفس مصفوفة الرسائل وسياق استجابة الأداة.
  - **التعطيل المؤقت الذكي (Cooldown):**
    - عند خطأ 429 أو 403: يُعطّل النموذج لمدة دقيقة واحدة (أو حسب رأس `Retry-After`).
    - عند خطأ 404 (نموذج متقاعد): يُعطّل النموذج لمدة ساعة كاملة.
    - النماذج المعطلة مؤقتاً تُتجاوز فوراً في الطلبات اللاحقة دون استهلاك محاولات.
  - **حماية حصة Gemini المجمعة:** إذا فشل نموذجان متتاليان من Gemini بخطأ 429 (نفاد حصة المشروع)، تُعطّل كل نماذج Gemini مؤقتاً لمدة 5 دقائق لتفادي استهلاك المحاولات هباءً.
  - **الأسرار الاختيارية:** `GROQ_MODELS` و `GEMINI_MODELS` لضبط قوائم مخصصة من أسماء النماذج مفصولة بفواصل حسب الترتيب المطلوب.
  - **حماية واجهة المستخدم:** عند تعذر جميع النماذج، تعيد الدالة رداً بحالة 200 برسالة عربية ودية ("المساعد الذكي مشغول قليلاً الآن، حاول بعد لحظات.") وتسجيل الخطأ في `console.error`.
  - **اختبار التحويل التلقائي:** تشغيل اختبارات الوحدة بالبيانات الوهمية عبر `deno test -A --no-config supabase/tests/ai_chat_failover_test.ts`.
- تطبيق قاعدة البيانات: شغّل migrations بحسب الترتيب، بما فيها `20261107000014_phase9_ai_chat_and_tools.sql`، ثم اختبر `supabase/tests/phase9_ai_tools_test.sql` بعد تجهيز مستخدمين ومتاجر اختبار في بيئة محلية مهيأة.
- شاشة `/java-export` متاحة للمالك فقط. تولّد `ProductRepository.java` وداخلها `Product`، تستخدم `BigDecimal` للقيم، وتهرّب النصوص؛ يتاح نسخ الكود وتنزيله ومشاركته.
- اختبار ترجمة وتوليد Java: `npx tsx tests/javaExportCompileTest.ts` (يتطلب Node وNix/OpenJDK `javac`).
- بناء التحقق: `npm run build`. لم تُطبّق migration أو اختبارات SQL على قاعدة Supabase فعلية في هذه المرحلة.

## 🔌 المرحلة 10: العمل دون اتصال والمزامنة التلقائية (Offline-First)

- **قاعدة بيانات محلية:** باستخدام مكتبة `Dexie.js` لإدارة IndexedDB في المتصفح وتطبيق الهاتف.
- **مزامنة تزايدية:** تحديث المنتجات والعملاء والتصنيفات دورياً عبر `updated_at`.
- **طابور الـ Outbox المحلي:** فواتير البيع دون اتصال تُسجل بمعرف `client_uuid` مع خصم متفائل للمخزون محلياً.
- **مزامنة متسلسلة تلقائية:** معالجة الفواتير فور عودة الاتصال بأمان تام بفضل خاصية منع التكرار (Idempotency).
- **كشف التعارض (Conflict Resolution):** فواتير نقص المخزون تُنقل إلى قائمة "تحتاج مراجعة" للمالك لمعالجتها يدوياً.
- **حماية العمليات الحساسة:** منع تعديل الأسعار، التعطيل، الإلغاء، والتحقق من PIN دون اتصال فعال.
- **مؤشر دائم وحماية الخروج:** شريط حالة دائم مع زر "مزامنة الآن"، وتحذير صريح عند تسجيل الخروج بوجود فواتير غير مُزامنة.
- للمزيد من التفاصيل المعمارية: راجع وثيقة [`docs/OFFLINE.md`](docs/OFFLINE.md).

يحتوي المستودع على اثنين من مسارات العمل (Workflows) الآلية داخل مجلد `.github/workflows/`:

#### أ) مسار فحص الجودة والاختبارات (`ci.yml`):
- يعمل تلقائياً عند إنشاء أي **Pull Request** إلى فرع `main`.
- يقوم بفحص الـ TypeScript (`npm run lint`) وبناء الواجهة واختبارات المزامنة المحلية وتصدير كود Java (`npm run test`).

#### ب) مسار بناء ونشر حزم أندرويد (`android-build.yml`):
- **عند دفع Tag إصدار (مثل `v1.0.0`):**
  - يبني نسخة الإنتاج الرسمية الموقعة (`Release APK`).
  - يستخرج `versionName` من اسم الـ Tag (مثلاً `1.0.0`)، ويزيد `versionCode` تلقائياً عبر رقم البناء (`github.run_number`).
  - يرفع ملف الـ APK كـ Artifact ويُنشئ **GitHub Release** رسمي ويرفق الحزمة تلقائياً.
- **عند عمل Push لفرع `main`:**
  - يبني تلقائياً حزمة تجريبية (`Debug APK`) لتجربة الميزات الجديدة ويرفعها كـ Artifact.
- **التشغيل اليدوي (`workflow_dispatch`):**
  - يمكنك تشغيل البناء يدوياً من تبويب Actions واختيار نوع البناء (`release` أو `debug`).

### 3. دليل توليد مفتاح التوقيع (Keystore) وإعداده في GitHub Secrets

لإصدار نسخ Release موقّعة وجاهزة للتثبيت المباشر على الهواتف، يجب توفير مفتاح توقيع رقمي (Keystore):

#### الخطوة 1: توليد المفتاح محلياً عبر أداة `keytool`
من سطر الأوامر على جهازك (تأكد من وجود JDK مثبت):
```bash
keytool -genkey -v -keystore grocery-pos-release.jks -alias grocery-pos-key -keyalg RSA -keysize 2048 -validity 10000
```
- سيطلب منك إدخال كلمة مرور للمفتاح وتأكيدها (احفظها جيداً!).
- سيطلب بيانات المتجر والاسم، يمكنك تعبئتها أو الضغط على Enter ثم تأكيد الإدخال بـ `yes`.

#### الخطوة 2: تحويل ملف المفتاح إلى نص مشفر بصيغة Base64
على نظام Linux أو macOS:
```bash
base64 -w 0 grocery-pos-release.jks > keystore_base64.txt
```
أو على Windows عبر PowerShell:
```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes("grocery-pos-release.jks")) | Out-File -Encoding ASCII keystore_base64.txt
```

#### الخطوة 3: إضافة الأسرار إلى مستودع GitHub
توجه إلى مستودعك في GitHub ثم:
**Settings** -> **Secrets and variables** -> **Actions** -> اضغط **New repository secret** وأضف الأسرار التالية:

1. `KEYSTORE_BASE64`: الصق النص الكامل الموجود داخل ملف `keystore_base64.txt`.
2. `KEYSTORE_PASSWORD`: كلمة المرور التي اخترتها للـ Keystore.
3. `KEY_ALIAS`: اسم المفتاح المستعار (في مثالنا: `grocery-pos-key`).
4. `KEY_PASSWORD`: كلمة المرور الخاصة بالمفتاح.
5. `SUPABASE_URL`: رابط مشروع Supabase (مثل `https://xxxx.supabase.co`).
6. `SUPABASE_ANON_KEY`: مفتاح Supabase Anon العام للعميل.

> ⚠️ **تحذير أمني صارم (Security Best Practices):**
> - **إياك ورفع ملف الـ Keystore (`grocery-pos-release.jks`) إلى المستودع إطلاقاً!** تأكد من وجوده في `.gitignore`.
> - **لا تُمرر مفتاح `SUPABASE_SERVICE_ROLE_KEY` أو مفاتيح الذكاء الاصطناعي (`GROQ_API_KEY`, `GEMINI_API_KEY`) إلى بيئة بناء العميل أبداً.** هذه المفاتيح مكانها الوحيد هو Supabase Secrets للـ Edge Functions.
> - **احفظ نسخة احتياطية آمنة من ملف الـ Keystore وكلمات المرور في مكان موثوق ومحمي:**
>   إذا فُقد هذا الملف، **فلن تتمكن من تحديث التطبيق على هواتف العملاء أو الكاشير مطلقاً**؛ لأن نظام Android يرفض تثبيت أي تحديث لتطبيق مثبت مسبقاً إذا كان موقّعاً بمفتاح مختلف، وسيتعين على المستخدم حذف التطبيق القديم وفقدان البيانات غير المُزامنة وتثبيت الحزمة الجديدة كلياً.

## 💾 دليل النسخ الاحتياطي واستعادة البيانات (Backup & Disaster Recovery)

### 1. النسخ الاحتياطي الكامل من داخل التطبيق (Application-Level Backup)
يوفر التطبيق للمالك إمكانية تصدير نسخة احتياطية مشفرة وشاملة بصيغة JSON:
1. افتح صفحة **الإعدادات** (`/settings`) أو **الاستيراد والتصدير** (`/import-export`).
2. انقر على **"تصدير نسخة احتياطية شاملة للمتجر"**.
3. يتطلب النظام إدخال رمز PIN الإداري للتحقق من هوية المالك.
4. يستدعي النظام دالة `export_full_store_backup` في PostgreSQL، والتي تجمع:
   - بيانات المتجر وتفضيلاته.
   - شجرة التصنيفات والمنتجات بالكامل مع أسعار التكلفة وتواريخ الصلاحية.
   - حسابات العملاء وسجلات الديون.
   - الفواتير التاريخية وتفاصيل لقطات الأسعار.
   - سجل حركات المخزون وحركات السداد.
5. يُحفظ الملف باسم `store-backup-[store-id]-[date].json` ويتاح تنزيله أو مشاركته.

### 2. النسخ الاحتياطي على مستوى قاعدة بيانات Supabase (Database-Level Backup)
لحماية كامل قاعدة البيانات من الكوارث:
```bash
# أخذ نسخة احتياطية كاملة للمخطط والبيانات عبر Supabase CLI:
supabase db dump --data-only -f backup_data_$(date +%Y%m%d).sql
supabase db dump --schema-only -f backup_schema_$(date +%Y%m%d).sql
```
أو عبر لوحة تحكم Supabase Dashboard:
- الذهاب إلى **Project Settings** -> **Database** -> **Backups** وتفعيل النسخ الاحتياطي التلقائي اليومي (Daily Automated Backups).

### 3. استعادة البيانات (Disaster Recovery & Restore)
- **استعادة من ملف SQL:**
  ```bash
  psql -h db.your-project.supabase.co -U postgres -d postgres -f backup_data_20261107.sql
  ```
- **استيراد المنتجات بعد كارثة عبر ملف Excel/CSV:**
  - يمكن استخدام ميزة **استيراد المنتجات الجماعي** لرفع قائمة المنتجات، حيث تقوم دالة `bulk_upsert_products` الذرية باستعادة التصنيفات والمنتجات ومخزونها فورياً مع معالجة تكرار الباركود عبر خيار "تحديث الموجود".

### 2. اختبارات التزامن في قاعدة البيانات (Database Concurrency & Idempotency Tests):
يتحقق النظام من أمان المعاملات الذرية ومنع النزول بالمخزون إلى قيم سالبة عند وجود طلبات متزامنة في نفس الأجزاء من الثانية:

- **سيناريو منع التكرار المتوازي (Parallel Idempotency)**: إرسال نفس الطلب بنفس client_uuid بالتوازي. النتيجة: تعيد الجلستان نفس الفاتورة دون أي تكرار لخصم المخزون.
